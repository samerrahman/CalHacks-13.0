# LOCK IN — validation and playtest plan

This is a plan for the future implementation, plus checks that run against the kit's pure reference utilities. It is not a claim that a rendered LOCK IN game, human playtest, or sponsor integration already exists. Keep actual observations separate from acceptance criteria.

## Run the kit checks first

Use Node 22 or newer; the utilities import JSON using standard import attributes and require no installed packages:

```sh
node --test lock-in-kit/reference/rules.test.mjs
```

If this kit is your working root, use `node --test reference/rules.test.mjs`. Also run the separate report reference tests and asset validator described in the kit README. A passing numerical model or asset-structure check does not replace an engine import, animation preview, source ownership review, or full playthrough.

The rule checks cover four-stage prerequisites, quiet/blackout preservation, bounded memory tempo, native-source-neutral sample acceptance, baseline coverage, sustained trends, graph continuity, sedation warning snapshots, pre-lure quiet defense, startup recovery, lure dominance, final arrival/seal, proposal rejection, public-data filtering, and independence of emergency actions from an eight-second provider wait.

## Implementation order and gates

1. **Target and assets.** Record OS, architecture, laptop resolution, Node/runtime versions, actual native SDK support, and available credentials without revealing values. Import every GLB and preview named clips. Decode every audio file. Inspect security stills and silhouettes. Verify the entry door is solid and never gains a gameplay open control.
2. **Offline loop.** Build the tutorial, four stages, Q/F quiet/restore, one graph-based creature, one ordinary and one accessible blackout, final route/seal, results, and restart. Use authored fallback tactics, captions, and effects. Demonstrate a complete win before provider integration.
3. **Readable exposure.** Check that machinery, footsteps, proximity, wall scrape, caption direction, and camera silhouette agree on position. Tune a human-achievable sequence of working, quieting, listening, and restoring. Keep every documented minimum and earned reward.
4. **Live services in order.** Validate the actual Gemini model and structured proposal; then the authorized ElevenLabs voice and current-state caption; then actual Presage capture/baseline/trend; then consenting Convex trace and reconnect. Follow the integration guide. Continue offline work when a credential/platform blocks one gate. Label live, cached, simulated, fallback, and untested separately.
5. **Report and cleanup.** Exercise opt-in local samples, realistic gaps and overlapping windows, end reports, deletion, pause/resume, camera loss, teardown, and a repeated run. Finally run typecheck/build/behavior checks and actual rendered input tests.

Do not create paid infrastructure, publish a public deployment, or send data elsewhere simply to fill a checklist. Use supplied authorized development services and document genuine blockers.

## Required deterministic gameplay cases

| Case | Procedure | Required observation |
| --- | --- | --- |
| First approach before a lure | Delay stage one until a warning, press Q near its end | Warning cancels; confidence/position do not reset instantly; four-second listening and actual retreat occur; a clear restore cue appears within 16 seconds |
| Boundary input | Timestamp Q immediately before warning expiry in the same simulation step | Defense succeeds; rendering order does not steal valid input |
| Early startup | Press F during close breathing, then Q at the next warning | Startup makes a clue, but no old warning resumes; a fresh approach/warning and Q escape remain available |
| Quiet camping | Leave Q active for several minutes | No task/research/containment progress; sedation reaches its capped final band; no hidden starvation mechanic appears |
| Active faults | Click five valid faults, then seven overload faults; deliberately click a quiet box | Correct progress counts exactly once; mistakes add bounded sound only; max two active faults and no invisible targets |
| Memory interruption | Enter two correct digits, force an eligible blackout, quiet, and restore | Same sequence, two inputs, cursor, tempo, and completed stages remain; free replay works |
| Memory tempo | Begin at UNKNOWN, STEADY, and ELEVATED; change trend during presentation | Four inputs in every case; multiplier never exceeds 1.20; current presentation never changes speed midway |
| Input timeout | Wait beyond 45 active seconds | Replay offered without a clang, death, research loss, or health requirement |
| First lure | Transmit correctly while creature is close and create a local mistake sound | Creature follows a continuous outward route; minimum 16 seconds protection survives sound/pulse/AI; arrival plus four-second hold may extend it |
| Second earned lure | Finish stage four before the first diversion ends and transmit B | New reward extends protection and takes a legal outward route; no hidden lockout or erased reward |
| Return from lure | Let reward end and create new local noise | Physical return is visible in derived cues; a fresh warning lasts at least six seconds; outward travel is not counted as a return approach |
| Final protocol | Try final T early, then complete four stages and transmit | Early control is disabled with a reason; valid broadcast follows the actual containment route and wins only after arrival plus three-second seal |
| Sedation boundary | Start a warning just before 90 or 180 seconds | Existing warning keeps its original duration; only later encounters use the new band |
| Blackout scheduling | Offer blackout during tutorial, warning, quiet retreat, lure, final seal, and cooldown | Ineligible failures are deferred; no earned protection or warning is hidden |
| Warning during blackout | Start an eligible blackout, leave residual noise running until an approach | Full warning sound and equivalent text appear; Q works without the terminal or distance display |
| Maximum pressure | Deliberately reach ALERT with several mistakes and ELEVATED simulated trend | Search/warnings stay within configured bounds; Q and earned lures still work; no pulse-only kill |
| Restart | Finish/lose/restart three times, including while a provider result is pending | New run IDs and single frame/input/sensor/audio subscriptions; late replies cannot act on a new run |

The future game needs complete valid defensive playthroughs across at least seeds 1, 17, 42, and 999. Test manual sensing first. Repeat representative runs with an explicitly simulated stable/elevated/unknown profile. This proves deterministic gameplay behavior, not live camera performance.

## Accessibility and presentation cases

- Complete a full run muted with directional captions. During blackout, the visual detector disappears while **approaching**, **near/listening**, **receding**, and **breach warning** remain available as sound-equivalent text. Do not reveal a forbidden live distance meter merely to compensate for muted audio.
- Complete a keyboard-only run. Check focus order, exact 1–4 button labels, Tab/Shift+Tab behavior, free R replay, T arming, Q from every station, hold-F and click-toggle restoration, pause focus, and restart. Native buttons keep their expected Enter/Space behavior.
- Run reduced-motion mode: no shaking required to identify a fault, no camera shake required to identify an attack, no flashing required for a waveform target. An optional fixed 1.00× memory speed preserves all win/report features.
- Inspect 1366×768, 1440×900, 1920×1080, and browser zoom 125%. No clipped warning, hidden emergency key, overlapped digit buttons, tiny captions, or developer trace covering the main task.
- Use a dim room background with a stable real desk light. In-game darkness must not require darkness on the player's face. Check safe capped master volume; threats remain understandable at low volume.
- Verify tutorial arrows point to actual controls after resize. The rehearsal cannot kill the player, can be replayed, and must explicitly teach Q/F before live danger begins. The creature remains unseen outside the monitor's truth-gated silhouette.

## Sensing and report failure matrix

Test native good capture, no permission, unavailable camera, stop capture, disconnected camera, poor light/motion, malformed payload, unsupported range, old receive-time, implausible measurement timestamp, accepted-to-rejected transition, baseline timeout, pause/resume, and native resource teardown. Unknown data is neutral immediately, even during minimum trend dwell. Never replace a lost live stream with simulated BPM.

Verify that 30 **usable** baseline seconds are counted after warmup; a paused or rejected interval cannot contribute. The established baseline stays frozen during the run. Test 12-second sustained elevation and recovery thresholds plus 20-second minimum state dwell. Nearby physiological clue stays at or below 0.18, is zero outside eight meters, and cannot satisfy the audible-evidence breach gate. Q and lure guarantees take precedence.

For reports, use the exact algorithm and fixtures in the dedicated report guide/reference. In particular check one-second bins, the ten-second pre-event window, post-event samples from +5 to +25 seconds, the five-second median peak, sufficient coverage, gap limits, overlapping events, same-capture-segment mapping, and qualified recovery. Missing/no-consent runs show unrecorded statistics. Verify timestamps across pauses using game-time/monotonic anchors. Public traces and logs contain neither raw pulse nor camera frames. Delete should remove the local report and, separately, any consenting remote session when authorized.

Do not ask a tester to hold their breath, induce distress, or lower their pulse. The test can use labeled fixtures to exercise exact thresholds. Live measurement observations are correlations, not a clinical assessment or proof of an emotional reaction.

## Provider and network failures

Use controllable fixtures before spending live quota. Delay a proposal to 7.9 seconds, then past eight seconds; alter the task, Q state, lure target, and allowed phase while it is in flight. Exercise malformed JSON, unsupported enums, mismatched request IDs/versions, stale evidence IDs, duplicate replies, rate limits, and service failure. Doors are not part of this game's action vocabulary. No result may invent a breach, position, puzzle answer, blackout, or arbitrary command.

During every pending call, press task buttons, Q/F, pause, and switch station. Verify the local clock and presentation never await a provider. Responses that expire, arrive after restart, or lose semantic eligibility must be rejected, with source and outcome shown honestly. A completed generated request does not prove its proposed action was applied.

For speech, verify exact caption correspondence, current encounter ID, same authorized creature voice, bounded volume, cancellation of obsolete instructions/taunts, and an audible/caption fallback when generation or decoding fails. Cache labels must identify a real prior generated result, never a bundled sound effect. The scripted tutorial and prepared lines remain usable without speech generation.

For Convex, test consenting session access, invalid capability rejection, event-sequence deduplication, reconnect, a second-screen subscription, no duplicated tactic/voice playback, and explicit session deletion. A local browser-channel judge view must identify itself as local and cannot be counted as a tested Convex deployment.

## What to measure and record

Use one row per actual attempt; leave untested rows explicit. Avoid fabricated target results.

| Field | Record |
| --- | --- |
| Build and target | Commit/build identifier, OS/architecture, display dimensions, runtime versions |
| Scenario | Seed, tutorial/manual/simulated/live mode, accessibility settings |
| Game result | Completed stages, win/loss reason, Q defenses, restore mistakes, warning minimum observed |
| Position consistency | Any disagreeing meter/audio/caption/feed evidence IDs |
| Performance | Measured frame-time median/high percentile, large stalls and when they happened |
| Director | Actual model, source, latency, applied/rejected/fallback, request/evidence IDs with secrets excluded |
| Speech | Voice/model configuration names, source, request-to-start latency, expiry/cancel behavior |
| Sensing | Time to first accepted estimate, usable baseline duration, rejected/stale intervals, explicit source |
| Report | Consent state, valid coverage, exclusions/overlap labels, no-data behavior |
| Human observation | Which instruction/control was misunderstood and whether it blocked completion |

Treat 4–7 minutes as a proposed normal-session pacing target, not a measured result. Tune intervals and voice length after at least three unfamiliar users attempt the tutorial and first complete run. Preserve fault totals, four-input memory, capped tempo, fair warnings, reliable Q/F, and earned lures. Document any tuning change with its observed reason.

The acceptance gate is a rendered, playable, inspectable build with recorded checks and accurate service status. This kit and its passing reference tests are preparation for that work.
